# bf1943-recomp

A native Windows x64 port of Battlefield 1943 (Xbox 360 / XBLA), built by statically
recompiling the PowerPC code with XenonRecomp. **Vulkan 1.3 is the only renderer.**
No game files or recompiled code are included: put your own dump in `original/`.

See [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) for the design and research notes.

## Build (renderer and tests)
Needs CMake ≥ 3.25, Ninja, MSVC (VS 2026), and the Vulkan SDK (`VULKAN_SDK` set).
```
vcvars64.bat
cmake -S . -B build\vk -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo
cmake --build build\vk
cd build\vk && ctest --output-on-failure
```
Recompiled game code (needs your own `original/v106/default.xex`; clang-cl from LLVM):
```
cd generated
..\build\xenonrecomp-clang\XenonRecomp\XenonRecomp.exe bf1943_config.toml ..\thirdparty\XenonRecomp\XenonUtils\ppc_context.h
cd ..
cmake -S game -B build\game -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_C_COMPILER="C:/Program Files/LLVM/bin/clang-cl.exe" -DCMAKE_CXX_COMPILER="C:/Program Files/LLVM/bin/clang-cl.exe"
cmake --build build\game
build\game\bf1943.exe --game original\v106 --user userdata
```
Launcher: `launcher/` (Electron, custom title bar; `npm install`, then `npm start`, or `npm run pack` for `dist\BF1943Launcher-win32-x64\BF1943Launcher.exe`). It finds `bf1943.exe`, the game files and the texture pack by itself, keeps its settings in `%APPDATA%\BF1943Launcher`, and starts the game with the chosen resolution, upscaling, shadows, frame rate, window size, HD textures and PBR materials.

PC controls (a connected pad also works): mouse = look (raw input, `--mouse-sens X`,
`--invert-mouse`), LMB = fire, RMB = zoom, wheel / 1 / 2 = toggle weapon, G / middle
button = grenade, F / V / 3 = knife, WASD = move, Shift = sprint, Ctrl / C = crouch,
Space = jump, R = reload, E = enter / use / pick up, Tab (hold) = score, Esc = menu,
Enter / Backspace / arrows = menu select / back / navigate. In menus (front end, the Esc menu and the spawn screen in a level) the cursor is free and the mouse works too: wheel = up/down, left click = select, right click = back; a click that closes a menu does not fire. Hold Alt to free the cursor in a level.
Frame rate: `--max-fps N` (30, 60, 120, 144...; default 120; 0 = uncapped), applied by the runtime at each swap. The client's simulation ticks at the same rate (uncapped: 120), so movement updates every frame and game time stays correct; the server keeps the console's 30 Hz. `--vsync` (keep the game's 2-vblank flips), `--vblank-hz N` (guest vsync rate, default 60).

Test options: `--capture N` (PNG every N s), `--capture-burst T` (8 frames back to back at T s, `frames/burst_N.png`, to see flicker), `--press "25:start,35:a"`, `--audio-wav out.wav` (record the output), `--headless`, `--toy-gpu`, `--dump-threads N` (every N s, log each guest thread's call stack, from the PDB). Reverse engineering: `--snap-mem "t1,t2,..."` writes the committed guest memory (heaps, about 1 GB each) to `snap_N.bin` at those times, to find game state by comparing snapshots; `--watch-write addr,size,t` logs the recompiled call stack of every write to that guest range from t seconds on.

Online: `--online-server <ip>`, `--gamertag <name>`, `--lan-ip <ip>`, `--port-offset N`. `--host` runs local games (e.g. the tutorial) as a LAN server on UDP port 1003 instead of in-memory (joining from another copy is not done yet). `--bots N` (with `--host`): once the server is up, N extra copies join it as players, without window or GPU emulation, each with its own ports and `<user>_botN` folder; they close with the host. A second copy started with `--host --port-offset 10` joins the first copy's game the same way (its client always connects to 127.0.0.1:1003). The bots are driven by an AI in the host (`runtime/bots.cpp`), modelled on DICE's Battlefield 1942/2 bots: a strategic layer gives each control point a temperature (neutral/enemy points hot, own points hot when enemies are near, cooled by distance and by team mates already going there) and each bot, a reactive agent, picks the most needed behaviour every tick: engage the nearest enemy within 70 m (aim, strafe, fire when on target), go to and hold its point (sprinting far from it), get unstuck (jump and side-step when it stops making progress), or confirm the spawn when dead. The host reads the server's soldiers and control points from guest memory and writes each bot's pad into shared memory; looking goes through the unclamped mouse path, so aim has no stick deadzone. Local games name every player "Player1", so the director finds which soldier is which bot by tipping one bot's view up and watching whose pitch rises. Tested on Wake Island with 1-2 bots: they are identified, pick points, leave their carrier, swim to the island and walk up the beach to their point. Not done yet: vehicles (boats, planes), line of sight (a bot shoots at enemies behind cover), navigation beyond straight lines plus unsticking; a US bot slows to a crawl in the water around x -360..-220 (cause unknown); combat not yet seen in a test. Debug: `BF_BOT_TRACE=1` logs every bot's state and pad every 2 s, `BF_BOT_POINT=N` sends all bots to control point N. `--host-map <Level>` (e.g. `Wake_island_s`) hosts that level once the title is past (with `--host`: a LAN server on UDP 1003; with `--online-server`: after the EA login). With both `--host` and `--online-server`, the hosted match is listed on Arcadia (its external-game port 42071, since the 360 game never registers its own match), and another copy's Quick Match finds it and gets the host's address. Joining stops there: the joining client wraps its traffic in EA's ProtoTunnel, and the host only builds its end on a Theater EGRQ for a game it created itself, so it ignores it (not solved yet). VDP sockets send plain UDP on the wire. Debug: `--log-ui` logs the menus' callbacks, `--ui-call name:args` fires one. `--args "..."` passes the game its own command line (engine switches such as `-listen <addr>` and `-Table.Member value` settings).

Display: `--res-scale N` renders at N× the console's 1280×720 (1–3, default 2 = 2560×1440; the shadowmap, drawn in 1024-wide pieces, stays native), `--sharpen fsr|cas|off` (AMD FidelityFX upscaling/sharpening when presenting, default fsr), `--window WxH` (window size, default 1280x720). On an RTX 5060 Wake Island runs at about 120 fps at 1×, 85 fps at 2×.

PBR: `--pbr [table]` swaps the lighting of selected game shaders for metal/roughness GGX lighting (sun, hemisphere ambient, cube-map reflections with an analytic environment BRDF), keeping the game's shadows, AO and exposure. The shaders and the registers to read are listed in `data/pbr_shaders.txt` (copied next to the exe; format in `runtime/xenia_shims/pbr_shaders.h`); the translator copies those registers and overwrites the lit colour (`thirdparty/xenia/src/xenia/gpu/spirv_shader_translator_pbr.cc`). Roughness and metallic come from the texture pack's normal maps (blue/alpha, any normal format: the translator reads them through an extra unswizzled "raw" binding, `*.pbr.rtex`); textures without pack data use the shader's fallback, derived from the game's specular power. The cube map is fetched a second time with a LOD bias of roughness × `blur` (default 6), so rough surfaces get blurred reflections. `tools/pbr_taps.py <--dump-shaders dir>` writes the table lines by following each shader's data flow (normal, view vector, albedo past the game's reflection blend, shadow, AO map, output, specular power). The table covers 37 of the 48 lit shaders seen on Wake Island; the 11 the script can't follow keep the game's lighting. Tested on Wake Island with `--capture` (carrier deck, hull, cranes, weapon; island buildings not checked up close).

Scene effects: `--scene-fx [key=value,...]` adds volumetric sun light and height fog to the HDR scene before the game's own bloom, exposure and HUD (`thirdparty/xenia/src/xenia/gpu/vulkan/scene_fx.cc`, shader `gpu/shaders/scene_fx.cs.glsl`; Vulkan compute, any GPU). Camera, sun and the three shadow-slice matrices come from the constants of the game's lit draws (vertex c0-c18, pixel c0-c7). When the game copies the world depth out (EDRAM depth base 720) the depth is saved; at the HDR scene resolve each pixel is ray-marched through exponential height fog, testing the game's own shadow map (read from guest memory, 3 tiled 1600x1600 24_8 slices) at every step, so shadowed air darkens (light shafts). The fog fades towards the sky colour measured just above the horizon (64 world-azimuth bins), so fogged surfaces meet the horizon whatever the game's tone mapping does; the sea, which has no depth, is a plane at the sea level measured from the waterline of hulls and beaches. Keys: `density` (0.0018 per metre), `height` (scale height, 80 m), `distance` (600 m), `steps` (32), `shafts` (0.6), `sky` (0.35, fog in front of the sky), `bias`, `base`, `debug` (1 distance, 2 shadow slices, 3 depth, 4 height, 5 haze colour, 6 invalid distances, 7 the shadow map slices, 8 screen-space shadows: dark where they shadow, magenta where the game's map says shadow, yellow facing away from the sun, blue on the sea (no shadows there), a magenta ring or line towards the sun and a top-left square red if the sun is in front, blue if behind; 9 ray-traced shadows: red where the traced ray hits a mesh, grey in the game's map shadow, dark facing away from the sun, blue on the sea, a green bar of one cell per thousand instances). Screen-space sun shadows: each surface pixel marches towards the sun through the world depth, so everything on screen casts at any distance, whatever the game's shadow pass leaves out; where the game's map already shadows, nothing is added. Keys `shadows` (strength, 1; 0 off), `shadow_length` (250 m), `shadow_steps` (48), `shadow_thickness` (2 m plus 2 % of the distance), `shadow_map` (0; 1 darkens the game's own map shadows a second time, for debugging). The saved depth of a 20e4 float depth target (D24FS8) is Xenia's host depth, which stores the guest's [0, 2) halved (`full_float24_in_0_to_1`), so it is doubled before the world position is rebuilt from it; before that fix every rebuilt distance was twice too long (found when blood pools 1.6 m under the eye matched a deck 3.2 m under it), so the haze and the shadow tests used points too far away. The slice matrices in c0-c10 take object positions like c12-c15, so they are multiplied by the inverse of the draw's world matrix (c16-c18) before use; without that, the map lookups (light shafts, debug views) showed false shadows and lit rectangles. Ray-traced sun shadows (`gpu/vulkan/scene_fx_rt.cc`, on GPUs with Vulkan ray queries; the device enables VK_KHR_acceleration_structure, VK_KHR_ray_query and bufferDeviceAddress when they are there, and the shader's `scene_fx_rt_cs` variant is built with `-DSCENE_FX_RT=1 --target-env vulkan1.2`): every world draw whose vertex shader computes clip = c12-c15 * p and world = c16-c18 * p, with p a fetched position (dotted directly as `rN.zxyw`, or after `cndeq rN, c255.xxxy, rM.zxyy, c255.yyyy`), has its mesh decoded on the CPU from guest memory (16- or 32-bit float positions, index lists or strips with restarts) into a bottom-level acceleration structure once; each frame a top-level one places the meshes with their world matrices. Static objects (seen with the same matrix in two frames) stay in it while out of view for 3 minutes, so casters behind the camera shadow what is on screen (a crane behind the carrier spawn now shades the deck); in view but not drawn, they are dropped. Each lit surface pixel then traces one ray to the sun, up to `rt_distance` (3000 m). The game draws the world in depth slices by distance (viewport z scale about 1 near, 0.002-0.009 further out, all into the same target), so draws are recorded whatever their depth range, from the frame's start to the world depth copy (the first-person weapon, sky and particles come after it). The foliage shaders (6581E327, 97727DA4, C942FBC6...) put the clip matrix in c16-c19 and the world matrix in c20-c22, and add a wind offset to the fetched position (`mad rN.xyz_, ..., c213.wwww, rM.xyzz`, left out); other `cndeq` swizzles (`.wxzz`) are read too. Alpha-tested draws are traced with their alpha: the pixel shader's texture fetch that gives alpha (all four components, or one into w, from an interpolator, or from twice it through `adds`) and the vertex attribute the vertex shader copies into that interpolator give each triangle's texture coordinates; the texture (DXT1/3/5, DXT3A/5A, 8 or 8888, tiled or linear) is read from guest memory once into a mask of where it passes the draw's alpha test (up to 256x256 bits), and the rays test it at every candidate hit on those triangles (non-opaque geometry, the instance's shader binding table offset pointing at its triangles' data after the normals). Where that can't be read the draw is left out (solid cards would cast). The terrain is traced as the whole heightmap: its vertex shaders (1B4EBA8B2370E9A7, ACDC14B71948C0B0) lift a 16-bit grid by a k_16 2048x2048 texture in tf22 (1 m a texel, world = (u, h, v) * c20 + c21, uv = grid * c22.xy + c22.zw); at its first draw the texture becomes 64 tiles of about 2.1 million triangles (every `BF_RT_TERRAIN_STEP` texels, 2; 1-16), rebuilt only when the heightmap changes (about 125 MB), so hills out of view cast. Shadow rays cull back faces, which only the terrain has (the meshes' instances opt out), so a ray starting just under the heightmap where a coarser patch is drawn is not blocked by it (`BF_RT_TERRAIN_FLIP` swaps the winding). Rigid multi-part models (vehicles and boats: one 3x4 matrix per vertex, rows `c[17+a0]`-`c[19+a0]`, with a0 a byte of the vertex, an 8_8_8_8 attribute, times c255.z in some shaders; one `maxas` in the shader) are split by that byte into one mesh per part, each placed by its own matrix, which is part to world (c12-c15 is the view and projection in those shaders; working the world out from the frame's view instead misplaced the parts in frames where the camera turned, so planes' shadows vanished and red ghosts of them showed in the deck's reflections); before, the landing craft weren't traced and showed the game's shadow-map acne as hatching on their hulls. Every added shadow fades in over n.l 0.02-0.12 (surfaces edge-on to the sun). Positions are rebuilt from the depth camera-relative (`inv_view_proj` maps NDC to world minus the camera, made in double on the CPU): from world coordinates hundreds of metres out, float precision stepped the view directions, so the positions and normals from the depth came out in a grid of blocks that moved as the camera swayed, and sun rays self-hit there (flickering shadows, worst on traced hulls). Left out: skinned meshes (soldiers: several bones blended per vertex), billboards (the far palms are camera-facing impostor cards, 3BBA6B72D31EAE8B, with computed texture coordinates; inside the shadow map's 300 m the game's map shadows them), the sea (an exactly flat mesh over 1 km wide; the effects model it as a plane). With `own_shadows` (1) the game's own shadow-map lookups in its lit shaders return lit (`IsGameShadowFetch`: a point-filtered 2D fetch at +-0.5 texel offsets of a texture also read by getWeights2D) and this pass draws every sun shadow: the traced ones, plus the game's map where its occluder (found from the map depth) is none of the traced meshes (soldiers); 0 keeps the game's. Debug views `debug=14` (the traced terrain from the eye), 15 (all traced meshes) and 16 (the alpha-tested ones): green where they meet the drawn surface, red in front, blue behind, black where nothing is hit. Keys `rt` (1; 0 off), `rt_distance`, `own_shadows`. Sea level: the waterline (an object pixel with sea, which has no depth, right below it) only counts where the ray just below it hits that object again nearby (a hull or beach going on under the water); below a deck's far edge, where the sea is seen beyond, it doesn't, and before that check the carrier deck became the sea level, so the deck got the sea's waves and reflections and lost its shadows. A traced mesh is never taken for the sea. Volumetric clouds (pass 5, half resolution, upsampled in pass 1): a layer `cloud_base` (1400 m) over the sea, `cloud_thickness` (1100 m) thick, cover `clouds` (0.45; 0 off), ray-marched in `cloud_steps` (32) with `cloud_density` (0.012 per metre) extinction; where clouds are comes from 2D noise kilometres across, worn by 3D noise near the camera, drifting with `cloud_wind` (10 m/s); lit by the sun (three steps towards it, forward and back scattering) and the sky, their brightness from the measured horizon sky so they match the game's exposure, fading into the haze far out. They hide what is behind them only beyond where the ray enters the layer. Cloud shadows: each lit surface takes the sunlight through the layer along the sun ray (four samples) and loses that share of the sun (`cloud_shadows`, 0.85). About 7 fps at 2560x1440 (68 to 61 on the carrier). Debug 17: the left half without the traced light, to compare it. Bounce rays that hit within `gi_contact` metres (2.5, 0 off) give back less than their cell's colour (down to a quarter at contact): corners, boat interiors and the deck under hulls darken, where the cache's average for the open, lit part of a cell cancelled out against the sky. A ray missing the cache also tries the neighbouring cell and the surface's second facing before falling back to a grey guess. Ambient occlusion (GTAO, on with --scene-fx, with or without rt): at half resolution from the depth, three slices of eight steps each way within `ao_radius` metres (2), filtered by depth into full resolution; it darkens the ambient share of the light and `ao_direct` (0.5) of the sun's, `ao` the strength (1, 0 off), none past `ao_distance` (250 m). Contact under wheels, wing roots, crane feet and vegetation. Debug 19 shows it, debug 20 the left half without it. Cost not yet measured cleanly (small next to the traced light). Fog on surfaces is capped at the haze in front of the sky in the same direction, so the far sea fades into the horizon (thinning the whole ray by a surface's distance left the sea beyond 300 m less hazy than nearer, a darker band). Water: what is seen through the sea is bent by its waves (pass 7 copies the scene with water pixels taken from a little aside, only from other water; `water_refract`, 1). With rt, four level rays just over the water find hulls and shores within `foam_width` metres (3): drifting foam along waterlines and beaches, and where the seabed is under half a metre or so; water hit all round within 8 m is inside a boat and left alone (`water_foam`, 1; fades out from 150 to 400 m). Shallow water over the seabed turns clearer and turquoise (`water_shallow`, 1). Debug 22: foam red, shallow green, at any distance. Muzzle flash light: while firing the game draws the world near the gun with a second version of its lit pixel shaders that adds a point light (c6 its position, about a metre from the eye; c7 its colour, flickering 0.04-0.54 against a sky ambient of about 1.4) fading only as 1 / distance and unshadowed, so it lit everything around. Those shaders are found by the vector to c6 in their code and that c6 near the eye (other lights, explosions, stay the game's); for world draws (before the depth copy) c7 goes to the GPU as zero, in the uploaded constants only, and pass 1 lights the world from the same point with the same colour, six times it over the squared distance, to nothing at `flash_radius` (6 m), shadowed by the traced meshes, on the surface's colour over the light the game gave it. The first-person weapon keeps the game's. `flash` (1; 0 keeps the game's light). Left as it was: the flash sprite (drawn by the game's instanced particle shader together with smoke and sparks). Parallax occlusion (--pbr): the pack normal maps carry the height (tools/texpack: alpha 191-253; roughness and metal share blue). At each table shader's normal map fetch the translator (spirv_shader_translator_pbr.cc, EmitPbrParallax) builds the surface frame from screen derivatives of the world position (r3 in every table shader) and of the fetch's coordinates (no tangents needed), marches the view ray down through the height field in eight fetches of the same map and takes the crossing between the last two; the shift becomes an equivalent screen displacement by which every later 2D fetch of the shader is moved in its own coordinates (PbrShiftFetch; not shadow-map or point-filtered fetches). Depth: 1.5 % of a texture repeat, at most `pom=` metres (0.03; per line in pbr_shaders.txt, BF_POM overrides the default), fading out by 45 m. The first-person weapon has pom=0 (a fixed depth made it noise). Procedural surface detail (pass 1, by world position): grime everywhere, more where the ambient occlusion hides the sky; on bare ground (the traced terrain, found by a short eye ray with the terrain mask, warm or grey, not grass, above the sea level) pebbles in Voronoi cells of `pebble_size` (0.09 m) in patches, each a sunlit dome with a contact shadow, and wobbly cracks `crack_size` (0.7 m) apart in dry patches; each fades out where it would be a few pixels, all by `detail_distance` (60 m); `detail` (1; 0 off). Debug 23: terrain red, pebbles green, cracks blue. Not seen up close yet (the test spawns are on the carriers). Main menu: `python tools/menu_patch.py --game original/v106 --user build/run/userdata` leaves Quick Match, Join Match with Friends, Create Private Match, Stats & Awards, Achievements, Leaderboards and Play Air Superiority out of the front end's main menu. The menu is an EA APT movie (Menu/main_nav.res in menu/main/mainmenu-00.fbrb, a BIGF archive of .apt, .const, .geo) whose script builds menuItems = [[flag, action, kind, clip], ...] in four lists (one per platform/trial branch); a left-out entry's bytecode becomes stack-neutral filler (dup, pop) so nothing moves, and the list's count drops. Entries are matched by their action (quickmatch, squad, cm, awards, achieve, leaderboard, startCoralSea), not their clip (item00...: screen slots that shift between lists). The archive is written to <user>/override/dist/xenon/..., with the payload gzipped again (a raw payload crashes the game); the runtime opens any file under <user>/override/ instead of the game's (files.cpp MapPath). Title screen: any key or mouse button gives Start until the game reads the profile (XamUserReadProfileSettings, which it does only once Start was taken), and its text reads PRESS ANY KEY. Mouse hover in menus: the APT menus only take the pad (the engine has _xmouse/_ymouse, properties 0x15/0x16, read from ints at 0x82D13ACC/0x82D13AD0 that nothing sets, and no menu script uses them), so every 2D draw whose vertex shader transforms FMT_32_32_FLOAT positions by c0-c3 (plus c9 where added) is kept each frame with its screen rectangle and colour c8 (gpu/vulkan/bf_menu.h, VulkanCommandProcessor::IssueDraw). The highlighted row is the filled green box (about 0.44, 0.56, 0.32); its list is the filled boxes with the same left and right edges and height (xgpu::MenuRows). Once the cursor moves onto another row of that list, the input code steps the highlight there with D-pad presses (50 ms on, 50 ms off), and a click waits until it is there; a still cursor leaves keyboard navigation alone. HDR: in the front end the top end is not stretched to the peak (bfhdr::no_stretch, set by the runtime when it enters or leaves the menus): the menus' near-white clouds and text went to the full peak and glared; in a level it is stretched as before; the front end also uses 65 % of the game's white (`--hdr-white`), as its full-screen bright clouds still glared. Back prompts can be clicked: pc_ui.cpp registers the Backspace key cell of the UI atlases it redraws (menu_common 87-110 x 29-52, popups 1-24 x 65-88; xgpu::AddBackIcon), the command processor keeps each frame's bitmap-fill draws (vertex shader 36821E5A: texture coordinates from c11/c12, origin at the icon's centre) whose tf0 is such an atlas and whose c11.w/c12.w fall in that cell, widened right over the label, and a left click there gives B instead of A. PC settings page (runtime/pc_settings.cpp): Help & Options' last entry reads PC SETTINGS (string table, was GAME CREDITS) and opens it instead of the credits (the input code sees that five-row list's last row selected when Enter, Space or a click on it comes); F10 opens it anywhere. Pages: graphics (look, resolution scale, upscaling, window size, frame rate limit, HDR and its brightness, HD textures, parallax, blood), effects (every scene effect: ray-traced and screen shadows, bounce light, ambient occlusion, clouds and their shadows, fog, light shafts, sea and surface reflections, water foam, refraction and shallows, surface detail, muzzle flash light), mouse (sensitivity, invert), keys (16 actions: Enter or a click, then any key or mouse button; a key taken from another action leaves it; a default second key stays while nothing else uses it) and profile (the multiplayer name). Live: the look between enhanced, toon, noir and WW2, the frame limit, HDR brightness, every effect (scenefx::Configure again), mouse and keys; the rest (marked RESTART) on the next start. Saved as they change to <user>/pc_settings.ini and, for the launcher's own options, its settings.json, which it passes on the next start. Drawn with GDI into a 1920x1080 image in the menus' style (white rows with a black rim, the selected one green, Bahnschrift condensed capitals, key-cap prompts) and shown over the window by a presenter UI drawer (bridge.cc OverlayDrawer, Xenia's immediate drawer); PQ-encoded at the HDR white when the output is HDR10. Mouse: hover, click, the arrows, right click or the Back prompt to go back. The game's own key icons still show the default keys. LAN games from the main menu (runtime/lan.cpp): tools/menu_patch.py now keeps Quick Match and Join Match with Friends, whose labels read HOST GAME and JOIN GAME (string table), and the input code opens PC pages for them instead (the main menu's four-row list, rows 0 and 1, on a fresh Enter, Space or click), so the game's online sign-in and matchmaking never run. HOST GAME: map (Wake Island, Iwo Jima, Guadalcanal, Coral Sea) and bots (0-15, joining as with --bots); START sets --host's LAN server and fires hostMultiplayerLocal(map) from the main loop (RequestHost), and answers browsers on UDP 19430 ("BF43?" -> "BF43!name|map|port"). JOIN GAME: a server browser (a broadcast plus this PC's loopback, a second to answer; name, map, address, reply time), REFRESH, and an address with its map to type. Joining hosts the same map locally (the game's own way to load it and start a client) with the client's packets to its own server (0.0.0.0:1003) sent to the host's address instead and the replies taken as from it (net.cpp FixAnyDestination/FixAnySource); on the same PC the joiner's ports are offset by 10. Tested with two copies on one PC: the second found the first in the browser, joined and loaded Wake Island from its server. Across two PCs not tested yet (the host's firewall must let UDP 1003 and 19430 in). Works on vertical lists (main menu, Help & Options); grids and horizontal choices are not covered. The game has no adaptive exposure (its tone map scales by a fixed pixel c3 = 0.25, the lit shaders' exposure c0 stays 4.0), so the few per cent darker sky measured while firing is the recoil tilting the view, not an exposure dip. Muzzle flashes and explosions: a colour-cache cell known for a while that is suddenly over 1.3 times brighter is not updated (the flash sprite and its light were learnt as the deck's colour, so the bounce light filled in the shadows around the player while firing), and horizon columns much brighter or darker than the measured sky (flash, smoke over the horizon) are left out of the haze colour. No measured frame-rate cost at the carrier spawn (83-84 fps either way). Without ray queries, casters off screen do not cast. The drawn sea gets none (water near sea level; far out the ray lands behind hulls and left dark streaks). About 1 ms at 2560x1440. Tested on Wake Island carrier spawns with `--capture` (both carriers, turning towards the sun with thick fog); light shafts are subtle at the default density.

Textures: `--textures <dir>` loads replacement textures made by `tools/texpack` (`install`); `--log-textures` logs every block-compressed texture the game creates with its hash and whether it was replaced. `--aniso N` sets N× anisotropic filtering (1–16) on the game's mipmapped textures; default 16, `0` leaves the game's own.

Looks: `--preset stock|enhanced|toon|noir|ww2` picks the graphics in one go (the launcher's Look row). `stock` is the game's own rendering (shadowmap 1024 at 100 m, vegetation LOD 1, no PBR or scene effects); `enhanced` turns everything on (`--pbr`, `--scene-fx` with its sun shafts, haze, screen-space and ray-traced shadows, the 1600 shadowmap at 300 m, 4x vegetation detail); `toon`, `noir` and `ww2` are enhanced plus a look on the final frame, HUD included, so every other feature (PBR, scene effects, ray-traced shadows, blood) stays on; `--preset stock --look toon` puts a look on the game's own rendering. Options after it still change it. `--look toon|noir|ww2` sets only the look: toon has four soft colour bands with the hue kept and dark outlines where the brightness changes; noir is hard black and white with film grain and a vignette, where only pure reds stay (deep red; skin and orange wood have too much green to count). ww2 is 1940s colour newsreel film: muted sepia-warm colour (reds and skin kept, greens faded, blues the most, so the sky is a warm grey rather than teal), lifted blacks and soft whites, 24 fps grain and flicker, a thin scratch in about one film frame in eight, and a vignette. Both run in the swap's gamma pass (`gpu/shaders/bf_look.xesli`, `bf_look_apply.xesli`, included by `apply_gamma_*.xesli`; parameters as push constants from `VulkanCommandProcessor::IssueSwap`, `gpu/vulkan/bf_look.h`), so they work with any `--sharpen`; no measured cost. HDR: `--hdr` (the launcher's HDR switch) presents an HDR10 swapchain (A2B10G10R10, BT.2020 with the PQ curve; instance extension VK_EXT_swapchain_colorspace) where the display offers one, which on Windows needs HDR on in the display settings; otherwise a warning is logged and the output stays SDR (`ui/vulkan/bf_hdr.h`, `VulkanPresenter`). The same gamma pass, after the look, takes the frame as gamma 2.2, stretches its top end (brightest component above 0.55 linear) smoothly up to the peak, converts BT.709 to BT.2020 and encodes PQ; the guest output is already 10-bit, so the paint to the swapchain only scales it. `--hdr-white` sets the game's white in nits (200; 80-500), `--hdr-peak` the highlights' peak (1000). Measured on the carrier spawn: median 28 nits, top 785. Screenshots and `--capture` frames hold the PQ values (they look washed out). Xenia's own overlays drawn into the swapchain are not converted. `--blood` adds gore, with any look (`gpu/vulkan/bf_gore.cc`): a soldier hit sprays a puff of blood and drops from the chest; a death leaves a pool; a soldier killed by an explosion (the killing blow's impulse over 1500, or a hit of 60 or more) comes apart: their body flies off in about six pieces (head, arms, legs, torso) that tumble, trail blood and lie on the ground, with a burst of blood and chunks. Pools, splats and chunks stay on the ground (the newest 160; small drops go first), until a level loads. The game's soldiers are skinned rigidly or with four weighted bones, their 3x4 bones read as `c[base+a0]` (base c17/c18 in the view, c5 in the shadow pass): at the death the bones of every skinned draw near the body are frozen, grouped into pieces (k-means from the head and the extremities) and moved with them for each draw (`VulkanCommandProcessor::IssueDraw`, the game's constants restored after it); the triangles joining two pieces are left out by drawing from an index list without them (built once per body and mesh from the vertex buffer's bone bytes into 4 MB of guest physical memory, `VGT_DMA_BASE` and the count pointed at it for the draw), and a mesh that can't be sorted is not drawn. The body stays in pieces as long as the game draws it. The blood is drawn by the scene effects pass against the world depth, before the HUD (it is hidden behind walls and under the HUD and the weapon): splats tint the surface under them, puffs, drops and chunks are lit sprites. Without `--scene-fx` (the stock preset) that pass runs with its effects off. Every soldier's health is a float (100 when full) at +0x3C of their soldier object, right after the vtable of its health part: the server's ServerSoldierEntity (vtable 82013A40, health part 820139F0) has the feet at +0x180 (x, y up, z), the last hit's impulse at +0x280 and the killing blow's at +0x120 (a bazooka at the feet: about 3100, mostly up); every copy of the game also has client soldiers (vtable 82007518, health part 820074F0, feet at +0x5D0). `runtime/gpu.cpp` HealthWatchThread reads the server's soldiers where this copy hosts, else the clients' (any game; without the impulse there only a hit of 60 or more bursts a body), scanning every 2 s and reading 30 times a second. The player's own hits make none (the game has its red vignette and hit arcs). Debug: `BF_GORE_TEST=1` fakes a hit on every soldier each 1.5 s (every third one a death that bursts the body), `BF_GORE_SELF=1` shows the player's own, `BF_GORE_LOG=1` logs the particles (in `xenia-gpu.log`, with each body that comes apart and its meshes' kept triangles). Tested with fake deaths on a bot on the carrier deck (the body flies apart in pieces with blood trails, pools and splats stay) and the player hitting themselves with a bazooka (100 -> 12, impulse 3105; then 18 -> 0, impulse 3141: a burst). Not seen yet: a real kill of another soldier, and how strong a bullet's impulse is.

Render settings go through `--args` like other engine settings. `--shadow-distance M` sets the sun shadow range in metres (default 300, `0` keeps the game's 100; with the 1600 shadowmap the slices are complete at any distance, at 300 m with coarser texels near the camera). Both are written into every copy of the engine's WorldRender settings once a level loads (the level brings its own copy, which `--args` misses). `--shadowmap N` sets the sun shadowmap size (default and maximum 1600; the game's own is 1024×1024 with 3 slices; `0` keeps it; an `--args` that sets a Shadowmap value wins). Each slice is drawn in one pass and must fit the 10 MB EDRAM as 32-bit depth, so 1600×1600 is the largest square: at 2048 the game draws and resolves only a 1040-wide strip of each 2048×2048 slice and the rest stays 0, so shadows falling there vanish (which half a receiver lands in moves with the shadow distance — the old "near shadows drop out above 100 m"). `--lod N` draws vegetation (palms, bushes) N times further in detail (default 4; `1` keeps the game's): it sets OvergrowthSettings.GlobalLodScale to 1/N in every copy (vtable 82040568, field table 82D33780). At 4 the far hills of Wake Island get their trees with no measured frame-rate cost; 10 costs a third of the frame rate for little more. `--overgrowth "Field=value,..."` writes other OvergrowthSettings fields (HiLodEnable, AdaptiveLodEnable, BillboardsEnable, MaxBillboardCount...) and logs them. Render.EdgeModelLodScale / EdgeModelScreenAreaScale and WorldRender MinScreenArea changed nothing visible at a distance (the far carrier is already at full detail). `--worldrender "Field=value,..."` writes WorldRender settings (ShadowmapViewDistance, ShadowmapSliceSchemeWeight, ShadowmapFirstSliceScale, ShadowmapMinScreenArea, ColoredShadowmapSlicesEnable...) into every copy, the level's included, and logs each copy's values once a level loads. Debug: a `show=<fetch address>` key in a `--pbr` table line draws that texture (e.g. the shadowmap fetch) at the pixel's screen position. Settings can also go in `<user dir>\XenonGameSettings.cfg` (the engine's own optional settings file, `GAME:\XenonGameSettings.cfg`, redirected to the user folder), one `Table.Member value` per line, e.g. `Render.ViewDistance 1234`; checked with `--log-settings`. `--dump-shaders <dir>` writes every shader the game uses (Xenos microcode and disassembly) once, as the first step towards replacement shaders. `--log-settings Table.Member,...` logs registered engine settings (`Game.*`, `Render.*`, `Client.*`; not `WorldRender.*`). The game's shadow pass leaves out the crane and most of what falls in the middle and far slices (`--scene-fx debug=7` shows the slices); `ShadowmapMinScreenArea=0,MinScreenArea=0.001,ShadowmapExtrusionLength=400` made no visible difference. `--scene-fx` screen-space shadows cover for it. `-Render.ViewDistance`, `-Render.EdgeModelLodScale` and `-Render.EdgeModelScreenAreaScale` made no visible difference.

## Layout
- `renderer/vulkan/`: Vulkan 1.3 core
- `tests/`: rendering tests that check real pixels
- `runtime/`: native host: guest memory, XEX loader, threads, kernel/XAM imports, PM4 command processor (sync packets only for now)
- `tools/`: `stfs_extract.py` (STFS package extractor), build helpers
- `thirdparty/`: XenonRecomp, VulkanMemoryAllocator, xenia (GPU and XMA subset, BSD-3, with its header-only deps), ffmpeg (libavutil/libavcodec subset with the xmaframes decoder, LGPL-2.1)
- `original/`, `generated/`, `research/`: local only, git-ignored
